# LEET 문항관리 확장 설계 — 다중 파일·오프라인 OCR·원본 자료실

작성일: 2026-10-08. 상태: 사용자 승인(오프라인 OCR 가능 여부에 대한 후속 설명 포함). 아직 새 기능 구현·새 EXE 배포를 완료한 것이 아니다.

## 목표와 확인한 요구

개인용 Windows 10/11 64비트 오프라인 프로그램에서 많은 문항 자료를 한꺼번에 등록하고, 다음 실행부터는 파일을 다시 선택하지 않고 찾아 편집한다. HWPX뿐 아니라 TXT, DOCX, MD, ZIP, PDF를 지원한다. 사용자는 스캔 PDF와 OCR 처리되지 않은 PDF도 많이 가지고 있다. 참고문헌을 실제 입력란에 채우고, 생성연도별 검색과 편한 베이지 화면을 제공한다. 등록 자료는 필요할 때 삭제하거나 복원한다.

기존 세트ID·문항ID, 문항별 해설·선택지 타당성, 공통/개별 키워드, 사용·기출 이력, 미확인 상태를 보존한다. 프로그램 실행과 OCR에는 로그인·네트워크·Python 별도 설치가 필요하지 않는다. 최종 프로그램은 `program.exe`이며 이미 승인한 GitHub 저장소 `iam-1004/-`에 새 버전과 소스를 저장한다.

## 기존 코드에서 확인한 문제

- `hwpx.propose_sections`는 `[해설 및 정답]` 뒤의 참고문헌만 찾는다. 본문 말미, Markdown 제목, 대괄호 표제, 다른 위치의 참고문헌을 놓칠 수 있다.
- `import_confirmed`는 HWPX 원본만 보관하고, 문항 세트 저장을 마쳐야 파일이 등록된다. 검토를 미룬 원본을 목록에서 다시 여는 기능이 없다.
- SHA256 중복 검사와 생성연도 정확히 일치 검색은 이미 있다. 다른 형식·휴지통·연도 범위·정렬에는 확장이 필요하다.
- 백업은 `.hwpx` 원본과 스키마 버전 1만 허용한다. 원본 자료실과 다양한 확장자를 함께 백업하려면 버전 호환 처리가 필요하다.

## 접근 방식

1. 기존 편집창에 여러 파일을 차례로 열기: 변경이 작지만 검토 창이 많아지고, 검토하지 않은 원본을 다시 선택해야 한다.
2. **권장: 원본 자료실에 먼저 등록하고 문항은 나중에 검토**: 원본·추출 원문·등록 상태를 영구 보관한다. 파일 등록과 문항 확정을 분리해 대량 처리와 중복 방지, 삭제 복구를 제공한다.

두 번째 방식을 채택하는 설계다. 문항 경계나 정답을 확신하지 못하면 초안으로 남기고 사용자가 원문을 배정한다. 형식이 다른 문서를 자동으로 검토 완료 처리하지 않는다.

## 가져오기 흐름

`여러 파일 / 폴더 / ZIP 선택 → 문서별 추출 또는 OCR → 중복 확인 → 원본 등록 → 결과표 → 문항 후보 검토 → 세트 저장`

- 여러 파일 선택, 폴더 선택, ZIP 내부 문서 탐색을 제공한다. 확장자 대소문자에 관계없이 처리한다.
- 결과표에는 원본 이름, 형식, 신규 등록/기존 자료/실패/텍스트 확인 필요, 오류·경고, 연결된 세트를 표시한다.
- 파일 하나가 실패해도 다음 파일을 처리한다. 진행률·현재 파일·취소를 제공한다. 취소 전 등록된 문서는 유지하고 등록되지 않은 임시 자료는 제거한다.
- 문서 등록은 원본·해시·추출 텍스트 저장까지 성공했을 때 완료로 표시한다. 프로그램을 껐다 켜도 원본 자료실에서 검토를 재개한다.
- 등록 직후 각 문서에 첫 세트 초안의 후보를 만든다. 후보 원문 배정·저장에는 기존 편집 흐름을 사용한다. 한 문서가 여러 제시문을 담으면 원문에서 범위를 선택해 추가 세트를 만들 수 있다. 임의의 번호 목록을 문항 세트로 단정해 자동 분할하지 않는다.
- 세트 생성에 원본 재선택이 필요하지 않다. 원본 파일은 문서와 세트에서 Windows 파일 연결로 열 수 있다.

## 지원 형식

| 형식 | 처리 |
|---|---|
| HWPX | 기존 문단 XML 추출을 유지하고 공통 후보 분리를 적용 |
| TXT | UTF-8/BOM, BOM이 있는 UTF-16, CP949를 엄격하게 해독. 인코딩을 확인할 수 없으면 실패 사유 표시 |
| MD | 원문을 그대로 보관. 제목·대괄호·글머리표를 고려해 문항 및 참고문헌 경계를 찾음 |
| DOCX | 본문 문단과 표 셀 텍스트를 문서 순서대로 추출. 헤더·각주는 별도 표시. 이미지·수식의 정확한 모습은 원본으로 확인 |
| ZIP | 지원 문서와 내부 ZIP을 제한 범위 안에서 처리. DOCX/HWPX 내부 ZIP을 자료 묶음으로 오인하지 않음 |
| PDF | 페이지별 텍스트 추출 및 필요한 페이지의 오프라인 OCR. 텍스트와 스캔이 섞인 파일도 처리 |

기존 바이너리 `.hwp`, `.doc`는 이 버전의 대상이 아니다. 지원하지 않는 형식은 결과표에 표시하고 다른 문서는 계속 처리한다.

## 스캔 PDF와 OCR

- PDFium으로 페이지를 읽고, 공백을 제외한 추출 텍스트가 40자 미만이거나 스캔 이미지가 페이지 면적의 60% 이상을 차지하면 OCR을 사용한다. 그 외의 텍스트 PDF에는 기존 텍스트를 우선 사용한다. 사용자가 전체 페이지 OCR을 명시적으로 다시 실행할 수도 있다.
- Tesseract와 한국어·영어·방향 검출 모델을 EXE에 포함한다. OCR 기본 언어는 `kor+eng`, 기본 렌더링은 300 DPI다. 페이지 회전 정보를 반영하고, 방향 검출 점수가 10 이상인 90/180/270도 회전은 보정한다.
- 페이지마다 텍스트 추출/OCR 사용 여부를 보관한다. 원문에는 페이지 구분을 남겨 근거 위치를 확인할 수 있다.
- PDF 원본 보기와 추출 원문을 함께 확인할 수 있는 비교 화면을 제공한다. 화면은 한 페이지씩 렌더링해 전체 PDF 이미지를 메모리에 쌓지 않는다.
- 파일별 `전체 페이지 OCR 다시 실행`을 제공한다. 저장된 원본을 사용하므로 파일을 다시 입력할 필요가 없다. 원문을 갱신할 때 기존에 편집한 세트·정답·해설을 자동으로 덮어쓰지 않는다.
- OCR 빈 결과, 읽기 실패, 평균 단어 인식 점수 60 미만, 정답·선택지 경계 누락은 검토 항목으로 표시한다. 음수 단어 점수는 평균에서 제외한다. OCR 점수는 정답의 정확도를 의미하지 않는다.
- ①~⑤, 표, 수식, 두 단 편집, 흐린 글자에는 인식 오류가 생길 수 있다. 인식 결과는 초안이며 실제 정답·생성연도·선택지 타당성을 추정하지 않는다.
- 암호화되어 읽을 수 없는 PDF는 실패 사유를 표시하고 다른 파일을 처리한다. PDF 원본에 없는 참고문헌을 만들어 넣지 않는다.

Windows 배포 의존성은 `pypdfium2==5.14.0`, `Pillow==12.3.0`, Tesseract `5.5.3`이다. Windows CPython 3.12 64비트용 배포 파일이 존재하는 것을 확인했다. 실제 조합의 실행 가능성과 EXE 포함은 구현 단계의 필수 검증 대상이다.

- 공식 Tesseract Windows 배포: `https://github.com/tesseract-ocr/tesseract/releases/download/5.5.3/tesseract-ocr-w64-setup-5.5.3.20260724.exe`
- 공식 자산 SHA256: `bee9e3434bd94fd65387d9be28cd467a41f61b1275383b55b0f59a1331270ae4`
- 공식 `tessdata_fast` 모델 기준 커밋: `87416418657359cb625c412a48b6e1d6d41c29bd`. `kor`, `eng`, `osd` 모델을 고정하여 사용한다.
- 다운로드 시 TLS, 배포 해시를 검증하고 PDFium·Tesseract·모델·Pillow 및 관련 라이선스를 함께 배포한다.

## 원본 보관과 중복

- DB 버전 2에 `sources` 문서 목록을 추가한다. 문서ID는 `F-...`이며 바뀌지 않는다. SHA256에 고유 제약을 둔다.
- 원본 이름·형식·원본 상대 경로·추출 텍스트·등록 시각·페이지별 추출 정보·검토 상태·휴지통 상태를 보관한다.
- 원본은 `originals/<SHA256>.<허용된 확장자>`로 보관한다. ZIP의 내부 이름을 디스크 저장 경로로 사용하지 않는다.
- 기존 세트 구조에 문서ID 연결을 추가한다. 세트의 원본 이름·해시·경로 표시와 세트ID·문항ID는 유지한다. 하나의 원본에서 여러 세트를 만들 수 있다.
- 이름이나 입력 폴더가 달라도 같은 바이트이면 기존 문서를 표시하고 다시 OCR/등록하지 않는다. 같은 ZIP을 다시 선택해도 내부 문서가 중복 등록되지 않는다.
- 휴지통의 문서도 중복으로 인식하며 복원 동작을 제시한다. 영구 삭제한 문서는 이후 다시 등록할 수 있다.
- 본문이 같아도 파일 바이트가 다른 문서는 자동으로 합치지 않는다. 형식 변환본·다른 판본에 있을 수 있는 원본 정보를 보존한다.
- 원본·추출 텍스트의 기록은 원본을 다시 선택하지 않고 다시 열어 볼 수 있어야 한다. 저장 도중 실패하면 DB와 원본 목록에 완료된 것처럼 남기지 않는다.

## 참고문헌

- `참고문헌`, `참고 문헌`, `[참고문헌]`, Markdown 참고문헌 제목, `References`를 문서 어디에서든 찾는다.
- 독립된 표제 행만 경계로 인정하고 문장 속의 '참고문헌'이라는 단어는 표제로 오인하지 않는다. 문헌의 숫자 목록을 문항 1·2·3 시작으로 오인하지 않는다.
- 제목부터 다음 문서 구조 제목까지의 실제 문헌 항목을 보존한다. 줄바꿈·목록·URL·연도를 그대로 저장하고, 다른 문항의 본문·해설이 문헌에 섞이지 않게 경계를 검증한다.
- 기존 `source` 필드를 유지하며 입력란 이름을 `출처 / 참고문헌`으로 명확히 표시한다. 편집·저장·재실행·검색·CSV·백업에 동일한 값이 유지된다.
- 이미 등록된 세트의 이 필드가 비어 있고 보관된 추출 원문에 참고문헌이 확인되면 채워 넣고 수정 이력을 남긴다. 사용자가 입력한 값은 덮어쓰지 않는다. 인식이 불확실하면 원문 배정으로 보완한다.
- 문헌의 발행 연도나 파일 날짜를 생성연도로 자동 입력하지 않는다. 문헌이 없는 자료는 공란으로 남기고 누락 점검에 표시한다.

## 삭제와 휴지통

- 원본 자료실에서 선택한 문서를 휴지통으로 이동하고 복원한다. 연결된 세트도 기본 목록에서 숨기되 기존 사용·기출·폐기 상태는 바꾸지 않는다.
- 특정 세트만 휴지통으로 이동할 수도 있다. 이 경우 같은 원본의 다른 세트와 원본을 보존한다.
- 영구 삭제는 휴지통에서만 가능하다. 삭제 전 문서·연결 세트·문항 수를 표시하고 사용자가 선택한다. 전체 자동 백업이 성공한 다음 삭제한다.
- 영구 삭제는 현재 자료실의 삭제다. 삭제 직전 자동 백업에는 복구를 위해 기존 자료가 남아 있다는 점을 삭제 확인 화면에 표시한다.
- 영구 삭제는 관련 문항·이력·세트 연결을 정리하고, 참조가 남지 않은 원본만 제거한다. 삭제 도중 실패하면 기존 상태로 복구한다. 최초 입력 파일이 있던 외부 폴더의 원본은 삭제하지 않는다.
- 편집창이 열린 자료의 삭제/복원/일괄 변경은 막거나 충돌로 알려 미저장 입력이 조용히 사라지지 않게 한다.

## 검색과 추가 문항관리 기능

- 생성연도 목록에서 단일 연도를 고르거나 시작~끝 연도로 검색한다. 미확인만 조회할 수 있고 연도 범위 검색에는 미확인 자료를 섞지 않는다.
- 생성연도·제목·등록일 정렬을 제공한다. 세트와 문항 화면, CSV 내보내기에 같은 검색 조건을 적용한다.
- 목록에서 여러 세트를 선택해 생성연도, 태그, 검토 상태를 일괄 변경한다. 공란 값을 실수로 일괄 삭제하지 않도록 변경할 필드를 선택한다. 미확인은 별도 선택이며 변경 전후 이력을 보존한다.
- `검토 필요` 점검에서 참고문헌, 제시문, 발문, 선택지, 정답, 평가 목표의 미입력과 OCR 경고를 모아 보여 준다. 이 중 보완이 필요한 항목으로 필터링하고 상세 편집창으로 이동한다.
- 초안은 누락이 있어도 저장할 수 있다. 검토 완료의 기존 필수 검증을 유지하고 일괄 변경에서도 검사한다.
- 사용자가 실제로 활용할 수 있도록 가져오기 결과를 CSV로 내보내고, 등록 파일에서 연결 세트로 바로 이동한다.

## 화면

기본 바탕 `#F3EBDD`, 입력 영역 `#FFFCF6`, 글자 `#3D352B`, 선택 배경 `#DEC9A6`의 베이지 계열을 적용한다. 주요 글자는 배경과 충분한 대비를 유지하고 선택/포커스/오류를 색만으로 구분하지 않는다.

메인 목록, 편집창, 원문 배정창, 원본 자료실, 가져오기 결과, PDF 비교, 휴지통, 스크롤 배경까지 일관되게 적용한다. 긴 글은 기존 줄바꿈·스크롤·Undo를 유지한다. 도구 모음에는 `자료 가져오기`, `등록 파일`, `새 세트`, `선택 자료 열기`를 중심으로 배치하고 백업·복원·내보내기는 자료관리 메뉴로 묶는다.

## 처리 구조와 한계

- 형식별 추출과 문항 후보 분리, 원본 저장, UI를 구분한다. 후보 분리는 HWPX 전용이 아닌 공통 텍스트 파서로 사용한다.
- PDF 렌더링/OCR/문서 추출은 별도 작업 프로세스에서 처리한다. Tk 화면과 SQLite 연결은 UI 프로세스에서 관리한다. UI는 진행 메시지를 주기적으로 받아 갱신하고 취소 때 작업을 종료한다.
- 선택한 입력을 임시 스냅샷으로 고정해 실제 보관하는 바이트와 추출한 텍스트가 일치하도록 한다. 단계별 임시 폴더는 성공·실패·취소 뒤 정리한다.
- 기본 제한: 개별 문서 25 MiB, PDF 500페이지, 추출 텍스트 2,000,000자, 단일 ZIP 100 MiB, 묶음 풀기 전체 250 MiB, ZIP 내부 항목 2,000개, 중첩 ZIP 3단계, 한 묶음 문서 500개. 초과하면 구체적인 사유와 파일을 표시한다.
- ZIP 경로 탈출·절대 경로·중복 경로·심볼릭 링크·암호화·크기 제한 위반을 거부한다. DOCX/HWPX XML의 DTD/엔티티를 허용하지 않는다.
- PDF 렌더링 이미지는 최대 40,000,000 픽셀로 제한한다. 페이지별 처리 시간 제한은 120초이며 초과한 파일은 원본을 보존한 검토 필요 상태로 남긴다. 이미지 크기에 맞춰 렌더링 배율을 줄이면 결과표에 표시한다.
- 원본 파일 미리 보기와 자동 문항 후보는 서식·수식·OCR 정확도를 보장하지 않는다. 원본과 실제 문항의 사람이 확인하는 절차를 유지한다.

## 기존 자료와 백업

- 기존 DB를 바꾸기 전에 버전 1 자료를 검증하고 원본 포함 자동 백업을 만든다. 자동 백업 실패 시 마이그레이션하지 않는다.
- 버전 1의 세트ID·문항ID·연도·원본·이력을 그대로 유지하고, 원본이 있는 자료에 문서ID 연결을 추가한다. 원본이 없는 수동 입력 세트는 그대로 사용할 수 있다.
- 마이그레이션은 트랜잭션으로 완료하거나 원래 DB를 유지한다. 새로 만든 빈 DB에는 버전 2를 직접 생성한다.
- 새 백업에는 문항으로 확정하지 않은 원본, OCR 원문, 휴지통, 모든 지원 형식의 원본도 포함한다. 백업 검증은 경로·해시·스키마·연결 관계를 검사한다.
- 새 프로그램에서 기존 버전 1 백업을 복원할 수 있게 한다. 버전 1을 먼저 검증한 후 마이그레이션한다. 버전 2 백업의 복원에서도 현재 자료 자동 백업과 실패 시 되돌리기를 유지한다.

## 완료 조건

1. 혼합된 HWPX/TXT/MD/DOCX/PDF/ZIP을 한 번에 등록하고 재실행 후 파일 재선택 없이 편집을 재개한다.
2. 글자 선택이 안 되는 한국어·영어 스캔 PDF, 회전 페이지, 혼합 PDF에서 실제 OCR이 실행되고 결과와 원본을 비교할 수 있다. 인식 오차는 검토할 수 있고 임의의 정답이 입력되지 않는다.
3. 같은 내용의 파일 바이트를 다른 이름·ZIP·폴더에서 다시 입력해도 문서와 세트가 중복 등록되지 않는다.
4. 여러 위치·표제의 참고문헌을 추출하고 기존 빈 참고문헌을 보완한다. 수정·재실행·검색·CSV·백업 후 값이 유지된다.
5. 휴지통·복원·영구 삭제를 검증하며 다른 세트의 원본·이력과 외부 입력 파일을 손상시키지 않는다.
6. 생성연도 정확히 일치·범위·미확인 검색, 정렬, 선택 자료의 일괄 수정과 수정 이력이 일관되게 동작한다.
7. 기존 버전 1 자료와 백업을 읽고 ID·원본·사용 기록을 보존한다. 손상 백업과 저장/삭제 실패 후 기존 자료를 유지한다.
8. 기존 33개 테스트와 새 가져오기·OCR·마이그레이션·휴지통·검색·UI 테스트를 실행한다. 한국어 OCR 검증은 실제 인식기로 수행하고 모의 결과로 대체하지 않는다.
9. `program.exe`에 OCR·모델·라이선스를 포함해 오프라인에서 실행한다. Wine 실행과 Windows PC 실기 검증 여부를 구분해 보고한다. 새 EXE의 시작·등록·재시작·중복 입력·스캔 OCR을 확인한다.
10. GitHub에 새 EXE와 소스를 저장하고 실제 다운로드한 바이트의 SHA256이 배포 EXE와 같은지 확인한다. EXE가 GitHub의 100 MiB 파일 제한을 넘으면 파일 일부를 빠뜨려 크기를 줄이지 않고, 사용 가능한 Release 업로드 경로를 먼저 해결한다.
